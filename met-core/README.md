# met-core

Rust workspace for the incremental (strangler) rewrite of the meticulous
backend. Phase 1 of the plan: see the `meticulous-backend-rust-mvp-plan`
note in the engineering vault.

## Crates

- **`crates/protocol`** (`met-protocol`) — typed, panic-free parser for the
  line-based UART protocol between the ESP32 and the backend. Pure: no IO,
  no globals, no async. Mirrors `esp_serial/data.py` plus the line dispatch
  in `machine.py`.
- **`crates/daemon`** (`met-daemon`) — phase 2: the serial daemon that owns
  the ESP32 UART + GPIO. Sans-IO read-loop state machine (`reader.rs`,
  a pure port of `Machine._read_data`: boot/reset watchdog, crash-trace
  collection, shot lifecycle timing, 500 ms disconnect alarm) driven by a
  transport — real serial (`tokio-serial` + Fika GPIO reset pins via
  `gpiod`, Linux only) or the fixture-replay emulator (same
  `emulated.*.json` files, same `action,start|stop|purge|home` reactions,
  same quirks). Publishes typed `MachineEvent`s (broadcast) and
  `MachineSnapshot`s (watch); encodes `action,` frames and hashed profile
  JSON (`send_json_with_hash` parity, md5-verified against CPython).

  Run it without hardware:

  ```sh
  cd met-core
  BACKEND=EMULATOR METICULOUS_EMULATION_DIR=../esp_serial/connection \
    cargo run -p met-daemon
  # stdin accepts: start stop tare purge home info reset bootloader pause resume
  ```

  What stays in Python on purpose (until phase 3+): sounds, shot/DB
  management, notifications, alarm UX, esptool flashing, config sync, REST
  and socket.io. The daemon reports; the backend decides.

Planned next (phase 3): `crates/ipc` — the Unix-socket contract that lets
Python's `Machine` become a thin client of this daemon behind a config flag.

## Parity testing

The crate is held to parity with the Python implementation by golden
fixtures in `crates/protocol/testdata/goldens/`, generated by running the
*real* Python parsers over emulator fixtures and hand-curated edge cases:

```sh
# from the repo root — regenerate whenever esp_serial/data.py changes
python3 met-core/tools/gen_goldens.py

cd met-core
cargo test          # golden parity + property tests (never-panic fuzzing)
cargo clippy --all-targets
cargo fmt --check
```

Ground rules encoded in the golden suite:

- Where Python parses successfully → same value, same socket.io JSON.
- Where Python logs-and-returns-`None` → `None`.
- Where Python raises an **uncaught** exception (crashing the read loop —
  the bug class this rewrite removes) → graceful `None`. Marked
  `"raises": true` in the golden files.

`unwrap`/`expect`/`panic!`/direct indexing are denied by workspace lints in
non-test code, so "panics are opt-in and greppable" holds by construction.

## Known, accepted divergences from CPython semantics

Documented in `crates/protocol/src/pynum.rs`; none are reachable with real
firmware output:

- Non-ASCII digits (e.g. `"١٢"`) are rejected; CPython `float()`/`int()`
  accepts them.
- Integers beyond `i64` are rejected; CPython has bigints.
- `float("inf")` inputs on `safe_float_with_nan` fields serialize as JSON
  `Infinity` in Python (invalid strict JSON) — such cases are excluded from
  goldens.
- Python's `safeFloat` returns the *int* `0` for non-finite input, so its
  JSON lexeme is `0` where Rust emits `0.0`. Same JSON number; golden
  comparison is numeric.
